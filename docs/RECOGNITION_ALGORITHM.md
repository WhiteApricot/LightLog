# 文字识别算法工作文档

本文记录 Phase 2 确定性文字记账算法的**当前实际实现**、已知缺陷和后续实验方向，供持续迭代时维护。识别系统的稳定边界、隐私规则和 OCR 设计以 [RECOGNITION.md](RECOGNITION.md) 为准；这里不重复通用原则。

## 当前流水线

```text
Raw Text
→ Normalize
→ 时间解析
→ 金额解析
→ 收支类型判断
→ 内容/商户提取
→ 关键词分类
→ RecognitionCandidate
→ 用户确认或修改
→ Repository
→ Transaction
```

实现入口为 `TextEntryParser.parse`。Parser 是无 UI、无数据库写入能力的确定性 Dart 代码；分类 ID 来自 Repository 提供的活动分类数据。

### Normalize

- 全角空格转换为普通空格。
- 常见全角 ASCII 字符转换为半角，`￥` 统一为 `¥`。
- 连续空白合并，去除首尾空白。
- 同时在 `EntryDraft` 中保留原始文本和规范化文本。

当前未做拼音、繁简转换、错别字纠正或同义词扩展。

### 金额解析

- 匹配带可选 `+` / `-`、最多两位小数及可选“元/块”的数字。
- 使用 `MoneyParser` 转换为正整数 `amountMinor`，不使用浮点金额。
- 唯一合法金额计入证据；没有金额、金额格式无效或出现多个金额都会生成 issue，阻止 Candidate 提交。
- `+` 明确推断为收入，`-` 明确推断为支出；无符号时继续依据关键词判断。

当前不能区分“原价、优惠、实付”等多金额语义，也不会猜测多个金额中的最终支付金额。

### 时间解析

- 支持 24 小时 `HH:mm`。
- 支持“昨天”“昨晚”“今天”“今早”“今晚”。
- `昨晚` 默认前一天 20:00，`今早` 默认当天 08:00，`今晚` 默认当天 20:00；显式 `HH:mm` 优先。
- 没有时间表达时使用解析时设备本地日期和分钟。
- Candidate 保存本地墙上时间及当时的 `timezoneOffsetMinutes`；正式入账仍由 Repository 转换为 UTC epoch milliseconds。

当前不支持完整年月日、星期、节假日、“前天”或自然语言时间范围。

### 内容/商户提取

- 从规范化文本中移除已消费的时间和唯一金额片段。
- 清理货币符号、首尾标点与重复空白。
- 剩余文本整体作为内容/商户候选，不凭空补全商户。
- 清理后为空会生成 issue。

当前没有商户别名归一化、门店识别或商品与商户的结构化拆分。

### 关键词分类

当前规则按固定优先级匹配：

- `工资/薪资` → 工资奖金 / 基本工资。
- `星巴克/咖啡/奶茶/饮料` → 餐饮 / 饮品。
- 餐饮关键词结合发生小时 → 早餐、午餐、晚餐或其他餐饮。
- `打车/出租/网约车` → 交通 / 打车。
- `公交/地铁` → 交通 / 公交地铁。
- 未命中 → 其他支出 / 未分类支出，或其他收入 / 未分类收入。

分类名称只用于规则查找，最终保存稳定的数据库分类 ID。父子分类不存在、不活动或类型不一致时 Candidate 不完整，不会写账。

### Confidence

当前 confidence 是可解释证据权重之和，并限制在 `0..1`：

| 证据 | 权重 |
| --- | ---: |
| 唯一合法金额 | 0.35 |
| 可用内容/商户 | 0.15 |
| 明确收支符号或关键词 | 0.15 |
| 默认按支出处理 | 0.05 |
| 明确时间表达 | 0.10 |
| 分类关键词命中 | 0.25 |
| 回退分类 | 0.05 |

confidence 目前只随 Candidate 保存，不触发自动入账。Phase 2 所有结果都必须由用户确认。

### Candidate、确认与正式入账

`RecognitionCandidate` 汇总 `EntryDraft`、分类 ID/名称、证据和 issues。只有金额、类型、内容、时间、时区偏移、一级分类、二级分类都存在且无 issue 时，才能转换为 `TransactionDraft`。

用户进入统一“记一笔”页面后，在顶部输入文字并主动点击“识别”，此时才调用 Parser；输入过程不做 debounce 或实时识别。完整 Candidate 在输入框下方展示分类、时间、金额和内容/商户，同时填入下方共用编辑表单。用户可直接点击结果卡的“确认入账”，也可继续修改金额、分类、内容、日期、时间和账户后使用表单保存；两条路径复用同一验证、`TransactionDraft` 构造和 `LedgerRepository` 写入逻辑。成功后标记 `source = text` 并保存 confidence，然后直接返回主界面。Parser 本身始终不能写库。

## 当前主要缺陷

- 商户识别依赖少量硬编码关键词，覆盖率和泛化能力较差；新增商户需要修改代码。
- 精确字符串与正则对简称、别名、错别字和相近字符不稳健。
- 分类词表很小，尚未利用本轮扩充后的完整分类体系。
- confidence 是固定加权规则，尚未按真实确认/纠正数据校准。
- 没有本地历史学习、冲突消解、重复检测联动或自动确认策略。
- 内容/商户仍是单一字符串，无法稳定拆分商品、门店和备注。

## Phase 3：五层本地混合识别器

以下方向属于 Phase 3，本轮只重排计划，不提前实现：

1. **Normalization**：在保留原文的前提下统一字符、空白和常见表达。
2. **Personal History**：使用本地确认、修改和撤销反馈形成个人证据。
3. **Merchant Knowledge Base**：维护商户规范名、别名、常见分类和本地确认统计，不联网查询；fuzzy matching 在明确阈值与冲突策略下处理简称和轻微错字。
4. **Category Lexicon**：将分类关键词、同义词、排除词和优先级分离为可测试、可维护的本地词表。
5. **Character n-gram classifier**：以本地样本训练轻量字符 n-gram 分类器，与确定性证据并行提供候选，不上传消费数据。

五层输出通过 **Evidence Fusion / Confidence** 合并，必须保留来源、冲突和可解释权重。原先独立规划的 Recognition Learning 不再单列阶段：基础学习并入 Personal History，更高级规则治理放入 Phase 3 后段或 hardening。

引入这些能力前必须先定义离线评估集、准确率/召回率指标、confidence 校准方法，以及用户纠正数据的保存和撤销语义。
